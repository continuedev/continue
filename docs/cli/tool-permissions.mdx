---
title: "Tool Permissions"
---

Every tool has one of three permission levels:

| Permission | Behavior |
|------------|----------|
| `allow` | Runs automatically, no prompt |
| `ask` | Prompts for approval before running (TUI only) |
| `exclude` | Hidden from the agent entirely |

## Defaults

Read-only tools (`Read`, `List`, `Search`, `Fetch`, `Diff`, `AskQuestion`, `Checklist`, `Status`, `CheckBackgroundJob`, `ReportFailure`, `UploadArtifact`) default to `allow`. `AskQuestion` is a built-in read-only tool that lets the agent pause and ask for clarification before continuing. Write tools (`Edit`, `MultiEdit`, `Write`) and `Bash` default to `ask`. In [headless mode](/cli/headless-mode), `ask` tools are excluded since there's no one to approve them.

## Overriding with flags

Use `--allow`, `--ask`, and `--exclude` to override defaults at launch:

```bash
# Allow file writes without prompting
cn --allow Write --allow Edit

# Exclude terminal commands
cn --exclude Bash

# Allow everything (headless automation)
cn -p "Set up the project" --allow "*"
```

Flags take precedence over all other permission sources.

## Tool matching patterns

Flags accept tool matching patterns:

- `Write` — matches any call to the `Write` tool
- `Write(*)` — same as above
- `Write(**/*.ts)` — matches `Write` calls where the primary argument matches the glob `**/*.ts`

```bash
# Allow writing only to TypeScript files
cn --allow "Write(**/*.ts)"

# Allow bash but not for install commands
cn --allow Bash --exclude "Bash(npm install*)"
```

## `permissions.yaml`

Persistent permissions are stored in `~/.continue/permissions.yaml`. This file is updated when you choose "Continue + don't ask again" in the TUI approval prompt.

```yaml
# ~/.continue/permissions.yaml
allow:
  - Read(*)
  - Write(**/*.ts)

ask:
  - Bash

exclude: []
```

You can edit this file directly, but it's primarily managed by the TUI. Changes take effect on the next session.

## Precedence

When multiple sources define a permission for the same tool, the highest-priority source wins:

1. **Mode policies** — `--auto` and `--readonly` override everything (see below)
2. **CLI flags** — `--allow`, `--ask`, `--exclude`
3. **`permissions.yaml`** — persistent personal settings
4. **Defaults** — built-in policies

## Modes

Modes are a shorthand for common permission sets. Switch modes with `Shift+Tab` during a TUI session, or set them at launch:

```bash
cn --auto       # Allow all tools without prompting
cn --readonly   # Plan mode — read-only tools only, no file writes
```

| Mode | Effect |
|------|--------|
| **normal** (default) | Uses configured permissions |
| **plan** (`--readonly`) | Excludes all write tools, allows reads and `Bash` |
| **auto** (`--auto`) | Allows everything — `*: allow` |

Plan and auto modes are absolute overrides. They ignore `--allow`, `--exclude`, and `permissions.yaml` entirely.

## `toolPermissions` rules in `config.yaml`

The same rules the IDE extensions use (see [`toolPermissions`](/reference#toolpermissions)) apply in the CLI when your assistant's `config.yaml` has a `toolPermissions` block:

```yaml
toolPermissions:
  allow:
    - runTerminalCommand(npm test*)
  ask:
    - runTerminalCommand(git push*)
  deny:
    - readFile(**/.env)
    - runTerminalCommand(terraform apply*)
```

They sit on top of the policies above. The order is: the CLI's own `exclude` (and the built-in safety check), then `deny` rules, then protected paths (`.env`, `~/.ssh`, `.git/`, and so on), then `ask` rules, then `allow` rules. So a `deny` rule refuses a call even if `--allow` or `--auto` would have allowed it, and an `allow` rule can run a call that the CLI policies would ask about, but never one that is excluded, denied or protected.

Rules cover the built-in tools `Bash`, `Read`, `Write`, `Edit`, `MultiEdit`, `List`, `Fetch` and `Search`. MCP tools are not covered in the CLI yet. When `config.yaml` has no `toolPermissions`, nothing changes.

**Headless mode** (`-p`). There is nobody to approve, so anything that would ask is refused: an `ask` rule, a protected path, or a call the reviewer would pass to a person. The model gets the reason as the tool result and is told not to retry or work around it.

## Auto reviewer (`--auto-review`, experimental)

```bash
cn --auto-review
cn -p "Fix the failing test" --ask Bash --auto-review
```

With `--auto-review`, a model with the `reviewer` role in your `config.yaml` (see [Reviewer role](/customize/model-roles/reviewer)) decides each call that your rules and the CLI policies leave to "ask": it allows it, asks you, or refuses it with a reason. The reviewer sees your messages and the earlier tool calls, never tool output. It cannot loosen a deny rule, a protected path, an ask rule or an exclude.

- Without a reviewer model, or if the reviewer fails or times out, a call is asked about in the TUI and **refused in headless mode**.
- Only calls whose CLI permission is `ask` reach the reviewer. In headless mode `Bash` is allowed by default, so pass `--ask Bash` (as above) to have the reviewer judge commands. Headless runs offer `ask` tools to the model only when `--auto-review` is on.
- After 3 refusals in a row or 20 in total, the reviewer stops allowing calls: the TUI asks you, and a headless run refuses. Tune these with `toolPermissions.auto.limits`.
- The conversation is sent to the reviewer model's provider. Use a local model if that matters.

| Flag | Effect |
|------|--------|
| `--allow <tool>`, `--ask <tool>`, `--exclude <tool>` | Override the CLI policies (unchanged) |
| `--readonly`, `--auto` | Plan and auto modes (unchanged; `deny` rules in `config.yaml` still apply) |
| `--auto-review` | Turn on the experimental reviewer for calls left open |

As AI systems get better, they're still held back by their training data and
can't access real-time information or specialized tools. The [Model Context
Protocol](https://modelcontextprotocol.io/introduction) (MCP) fixes this by
letting AI models connect with outside data sources, tools, and environments.
This allows smooth sharing of information and abilities between AI systems and
the wider digital world. This standard, created by Anthropic to bring together
prompts, context, and tool use, is key for building truly useful AI experiences
that can be set up with custom tools.

## How MCP Works in Continued

Currently custom tools can be configured using the Model Context
Protocol standard to unify prompts, context, and tool use.

MCP Servers can be added to your config using `mcpServers`.

<Info>MCP can only be used in the **agent** mode.</Info>

For ready-to-use configurations for popular MCP servers, see [Example MCP Servers](./mcp-examples.mdx).

## Quick Start: How to Set Up Your First MCP Server

Below is a quick example of setting up a new MCP server for use in your config:

1. Create a folder called `.continue/mcpServers` at the top level of your workspace
2. Add a file called `playwright-mcp.yaml` to this folder
3. Write the following contents and save

```yaml title=".continue/mcpServers/playwright-mcp.yaml"
name: Playwright mcpServer
version: 0.0.1
schema: v1
mcpServers:
  - name: Browser search
    command: npx
    args:
      - "@playwright/mcp@latest"
```

Now test your MCP server by prompting the following command:

```
Open the browser and navigate Hacker News. Save the top 10 headlines in a hn.txt file.
```

The result will be a generated file called `hn.txt` in the current working directory.


## Using JSON MCP Format from Claude, Cursor, Cline, etc

<Info>
If you're coming from another tool that uses JSON MCP format configuration files (like Claude Desktop, Cursor, or Cline), you can copy those JSON config files directly into your `.continue/mcpServers/` directory (note the plural "Servers") and Continued will automatically pick them up.

For example, place your JSON MCP config file at `.continue/mcpServers/mcp.json` in your workspace.
</Info>

## How to Configure MCP Servers

To set up your own MCP server, read the [MCP
quickstart](https://modelcontextprotocol.io/quickstart) and then add an MCP
server block to your [config file](./configuration.mdx):

```yaml title="config.yaml"
# ...
mcpServers:
  - name: SQLite MCP
    command: npx
    args:
      - "-y"
      - "mcp-sqlite"
      - "/path/to/your/database.db"
# ...
```

<Note>
When creating a standalone block file in `.continue/mcpServers/`, remember to include the required metadata fields (`name`, `version`, `schema`) as shown in the Quick Start example above.
</Note>

### How to Configure MCP Server Properties

MCP components include a few additional properties specific to MCP servers.

- `name`: A display name for the MCP server.
- `type`: The type of the MCP server: `sse`, `stdio`, `streamable-http`
- `command`: The command to run to start the MCP server.
- `args`: Arguments to pass to the command.
- `env`: Secrets to be injected into the command as environment variables.

### How to Choose MCP Transport Types

MCP now supports remote server connections through HTTP-based transports, expanding beyond the traditional local stdio transport method. This enables integration with cloud-hosted MCP servers and distributed architectures.

#### How to Use Server-Sent Events Transport (`sse`)

For real-time streaming communication, use the SSE transport:

```yaml
# ...
mcpServers:
  - name: Name
    type: sse
    url: https://....
# ...
```

#### How to Use Standard Input/Output (`stdio`)

For local MCP servers that communicate via standard input and output:

```yaml
# ...
mcpServers:
  - name: Name
    type: stdio
    command: npx
    args:
      - "@modelcontextprotocol/server-sqlite"
      - "/path/to/your/database.db"
# ...
```

#### How to Use Streamable HTTP Transport

For standard HTTP-based communication with streaming capabilities:

```yaml
# ...
mcpServers:
  - name: Name
    type: streamable-http
    url: https://....
# ...
```

These remote transport options allow you to connect to MCP servers hosted on remote infrastructure, enabling more flexible deployment architectures and shared server resources across multiple clients.

For detailed information about transport mechanisms and their use cases, refer to the official MCP documentation on [transports](https://modelcontextprotocol.io/docs/concepts/transports#server-sent-events-sse).

### How to Sign In to Remote MCP Servers (OAuth)

Remote servers (`sse` and `streamable-http`) that use OAuth need no extra configuration:

```yaml
mcpServers:
  - name: Datadog
    type: streamable-http
    url: https://mcp.datadoghq.eu/api/unstable/mcp-server/mcp
```

1. If the server answers a request with HTTP 401, the server shows **Sign in required**. Continued never opens a browser by itself.
2. Choose **Sign in** (the person icon next to the server, or the server's menu). Your browser opens the provider's sign-in page, and when you finish you are connected.
3. The access token is refreshed automatically when it expires. If the provider revokes your session, the server goes back to **Sign in required**.
4. **Sign out** (server menu) removes the stored credentials.

**Sign in is always offered for remote servers**, including ones that reject a connection in a way Continued can't recognise as an OAuth challenge.

The browser is sent back to a small local server while you sign in, on port `3000` by default. If that port is in use you'll see an error naming it; choose another with `oauth.callbackPort`. Some providers only accept a pre-registered redirect URL, so use the port that was registered:

```yaml
mcpServers:
  - name: Atlassian
    type: streamable-http
    url: https://mcp.atlassian.com/v1/mcp/authv2
    oauth:
      callbackPort: 3456
```

If sign-in fails or is abandoned (denied in the browser, a wrong code, or no response for 5 minutes), the partial registration is cleared so the next attempt starts clean.

<Note>
  OAuth credentials (access and refresh tokens, client registration) are kept in
  the editor's encrypted secret storage. Hosts that can't store secrets, such as
  the CLI, fall back to `~/.continue/index/globalContext.json`; treat that file
  like any other credential store. Credentials saved there by earlier versions
  are moved into secret storage the first time they are used.
</Note>

### How to Use MCP Servers Behind a Proxy or TLS Inspection

Remote MCP servers (`sse` and `streamable-http`) use the same `requestOptions` as models, so they work behind an HTTP(S) proxy and a TLS-inspecting firewall without tools like `mcp-remote`:

```yaml
mcpServers:
  - name: Datadog
    type: streamable-http
    url: https://mcp.datadoghq.eu/api/unstable/mcp-server/mcp
    requestOptions:
      useSystemCa: true # trust the OS certificate store (default on Windows and macOS)
      # caBundlePath: /path/to/corp-root.pem
      # proxy: http://proxy.corp:3128
      # noProxy: [".internal.example.com"]
```

- `useSystemCa`, `caBundlePath` (and `NODE_EXTRA_CA_CERTS`), `proxy` / `noProxy` (and `HTTPS_PROXY` / `NO_PROXY`), `clientCertificate` and `verifySsl` all apply. `verifySsl: false` now takes effect (it was previously ignored).
- They apply to every request: the MCP connection itself, OAuth discovery, client registration, the sign-in token exchange and token refresh.
- To set them once for everything, put `requestOptions` at the top level of `config.yaml`; per-server values take precedence.
- If the certificate isn't trusted, the error says so and points at `useSystemCa` and `caBundlePath`.

**stdio servers** run in their own process, so Continued can't change their networking. For Node-based servers (for example `npx ...`), Continued sets `NODE_OPTIONS=--use-system-ca` so they trust the OS certificate store too. This is on by default on Windows and macOS, can be turned off with `requestOptions: { useSystemCa: false }` at the top level, and is skipped when the `node` on your PATH is too old to know the flag (Node 22.15 or newer is needed). Anything you set in the server's own `env.NODE_OPTIONS` is kept.

### How to Work with Secrets in MCP Servers

With some MCP servers you will need to use API keys or other secrets. You can leverage locally stored environment secrets.

```yaml
# ...
mcpServers:
  - name: Supabase MCP
    command: npx
    args:
      - -y
      - "@supabase/mcp-server-supabase@latest"
      - --access-token
      - ${{ secrets.SUPABASE_TOKEN }}
    env:
      SUPABASE_TOKEN: ${{ secrets.SUPABASE_TOKEN }}
  - name: GitHub
    command: npx
    args:
      - "-y"
      - "@modelcontextprotocol/server-github"
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: ${{ secrets.GITHUB_PERSONAL_ACCESS_TOKEN }}
# ...
```
